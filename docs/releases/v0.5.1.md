# v0.5.1: the bundle and the CLIs, published

**Release status:** prepared on 2026-09-24. Not yet tagged.

## Objective

Publish `execMotion` and the three CLIs to the registry, next to the
libraries, so that another repository can pin them by digest.

v0.5.0 published the seven libraries and only attached the bundle and the
tools to the GitHub release. No consumer could have named them: an `ost`
descriptor had no way to pin a bundle or a tool from another repository.
`ost` 0.23.4 added both:

- `requires.bundles[].artifact` takes the same per-target pin table as a
  library.
- `requires.tools[]` pins a published tool for a bundle's tests and puts its
  executable on the session's `PATH`.

## Why it is needed now

`usd-vrm-plugins` holds the last copy of generic motion code outside this
repository: its `plugins/execMotion`. Its `execVrm` reads `execMotion`'s
nodes by name at run time. Its migration rule says the OpenExec parity rows
must be re-run against the consumed bundle before its copy is deleted. That
takes a pin, and a pin needs an artifact in a registry, which is what this
release provides.

## What ships

Everything v0.5.0 shipped, rebuilt at 0.5.1. There is no behaviour change in
any library, bundle or tool. The differences are all in publication:

| Member | v0.5.0 | v0.5.1 |
| --- | --- | --- |
| seven libraries | release asset + registry | release asset + registry |
| `execMotion` | release asset only | release asset + registry |
| `motion_convert`, `motion_bvh_inspect`, `motion_record` | release asset only | release asset + registry |

- Every artifact goes to `ghcr.io/animu-sphere/usd-motion-plugins`, tagged
  `<member>-0.5.1-<target>`, for the same three targets.
- The pin table (`external-library-pins.md` / `.json`) has one section per
  kind: `libraries`, `bundles`, `tools`. The Markdown form is ready to paste
  under `requires.libraries`, `requires.bundles` or `requires.tools`.
- The publish job counts each kind from the tree, so a member that stops being
  packaged fails the job instead of leaving a gap in the table.

## How it was checked before the tag

- The whole workspace ran under `ost` 0.23.4 on Windows: root `ost build` and
  `ost test` (53 of 53), `ost plugin build` and
  `ost plugin test --up-to 5` for `execMotion`.
- `ost plugin package --workspace` writes a dist directory for the bundle and
  for each tool, each with `manifest.json` and an SBOM. Every one of them
  imported, and `ost artifact push` to a throwaway local registry returned the
  artifact digest it was given plus an OCI digest. Those are the two fields
  the publish job reads.
- In `usd-vrm-plugins`, on a scratch branch: `plugins/execMotion` was deleted
  and `execVrm` pinned that locally built bundle. `ost plugin test` then
  materialized it and put it on the session's plugin path. Run inside
  `ost plugin run`, the four `execVrm` exec suites, `workspace_exec_driver`
  and the five `workspace_exec_parity_*` cases all passed against it.

What was not checked before the tag is the push to GHCR itself. The v0.5.0
tag proved the library half of that, and this release uses the same credentials
and the same command for the new rows.

## Known limitation for the consumer

`usd-vrm-plugins` can pin this bundle but cannot yet delete its copy. The
root `ost build` / `ost test` materializes external *libraries* only, so its
root CTest suites that compose `execMotion` would have none to load. That is
an ask to `ost`, not to this repository.
